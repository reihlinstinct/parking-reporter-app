# Address lookup builder (open data, attributed)

`tools/address-lookup/build_address_lookup.py` regenerates the app's
address lookup (`{"version": 1, "streets": [...], "addresses": [...]}`)
from open, attributed sources. It replaces the municipality-supplied
`addresses.json`, whose licence for publication was never established
and which is therefore kept out of this repository.

## Sources and licences

1. **Street codes and names** - the national street registry "רשימת
   רחובות ישראל" (רשות האוכלוסין וההגירה) on **data.gov.il**
   (resource `9ad3862c-8391-4b2f-84a4-2d4c68625f4b`, locality 3000 =
   Jerusalem). Its סמל_רחוב is the municipal street code the 106 API
   uses (spot-checked: אגריפס -> 613). The dataset page carries **no
   dataset-specific licence**, so the site's default licence applies by
   its own terms: "תנאי השימוש באתר מאגרי המידע הממשלתיים"
   (<https://data.gov.il/terms-of-use>, updated 2025-08-30) - a
   worldwide, royalty-free, non-exclusive licence to use, copy,
   distribute and create derivative works, subject to **citing the
   source**, no misleading presentation or distortion, and no unlawful
   or privacy-violating use. Per those terms, the licence in force at
   retrieval time governs; this build was retrieved 2026-11-08. The app
   cites the source on the Settings -> Licenses screen.
2. **Address points (house numbers)** - **© OpenStreetMap contributors**,
   <https://www.openstreetmap.org/copyright>, licensed **ODbL 1.0**
   (<https://opendatacommons.org/licenses/odbl/1-0/>), fetched from the
   Overpass API inside the Jerusalem municipality boundary (OSM relation
   1381350, mapped to an Overpass area with `map_to_area`).

## Licence status of the output

Under ODbL 1.0 section 1 ("Derivative Database": a database based on the
ODbL-licensed database) and section 4.4(b):

- The **addresses section** of the generated file is a **Derivative
  Database** of OpenStreetMap. It is itself available under ODbL 1.0,
  and the generated file carries top-level `"attribution"`
  ("© OpenStreetMap contributors") and `"license"` (ODbL-1.0 URL)
  keys so the notice travels with the data. Both loaders (the helper
  pipeline's `Addresses` and the app's `StreetDirectory`) read only the
  `version`/`streets`/`addresses` keys and ignore the notices.
- The **combined file** (streets section beside the addresses section)
  is a **Collective Database** under section 4.5(a): the streets section
  keeps its own status (section 1 above) and is not re-licensed.
- The **individual address lookups** the app produces at runtime are
  **Produced Works**; the attribution shown on the Settings -> Licenses
  screen covers section 4.3's notice requirement for them.

Section 4.6 (making the Derivative Database available): recipients can
reproduce the addresses section byte-identically by running the
generator in this repository with the pinned inputs recorded below,
under the boundary condition stated there; it is distributed under
ODbL 1.0. (Owner decision 2026-11-09: the generator route, no release
asset.) Its sha256 is taken over canonical compact JSON
(`json.dumps(addresses, ensure_ascii=False, separators=(",", ":"))`);
the builder prints it on every run, and
`validate_lookup.py --addresses-sha256` checks it with the same
expression. The value from the 2026-11-08 reference build is
`2b45e56d41364df6262adc321424d71a8a0851f6873ff17a55e65ed82665c657`
(see "Reference build" below for how current it is).

The same notice appears on the app's Settings -> Licenses screen.

## Reproduce

```bash
python3 tools/address-lookup/build_address_lookup.py --out addresses.json
python3 tools/address-lookup/validate_lookup.py --candidate addresses.json \
    --addresses-sha256 <printed addresses-section sha> [--sha256 <printed whole-file sha>]
```

The run prints row counts, the pinned inputs, the Overpass database
timestamps (`osm3s.timestamp_osm_base` and `timestamp_areas_base`, when
the server reports them) and both sha256 values to stderr.
`--addresses-sha256` is the check for the ODbL part; the whole-file
`--sha256` also covers the streets section, which drifts with the live
registry (below). Inputs are pinned as follows:

- Overpass query: `[date:"2026-11-08T00:00:00Z"]` as the global setting,
  then `rel(1381350); map_to_area->.jerusalem;` in the same query, then
  `addr:housenumber` + `addr:street` nodes and ways in that area
  (`out center tags`). The date pin covers the address nodes and ways
  and the relation lookup. It does **not** cover the boundary geometry:
  the Overpass documentation states that areas derived from relations
  always represent current data, and that `map_to_area` returns the
  area as last generated by the server's background process
  (<https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL>,
  "By area" and "map_to_area"). So the addresses section is
  byte-identically reproducible **while the boundary relation 1381350
  (and the server's area generated from it) is unchanged**; a later edit
  to the boundary can add or drop points near its edge. The printed
  `timestamp_areas_base` shows which area state a run used.
- National registry resource `9ad3862c-8391-4b2f-84a4-2d4c68625f4b`,
  filter סמל_ישוב=3000, retrieved 2026-11-08, 4,383 records at
  retrieval (4,371 kept, 6 ambiguous name pairs dropped). The registry
  is a live dataset (updated about weekly) and its API has no date pin,
  so a later re-run may pick up registry changes in the streets section;
  the addresses section above is the pinned part (with the boundary
  condition above).

Reference build of 2026-11-08, made with the earlier query form
(`area(3601381350)->.jerusalem;`, the same Overpass area that
`rel(1381350); map_to_area` selects) before the change to
`map_to_area`: 4,371 streets, 22,524 address points, whole-file sha256
`bd1d8f5d49549cfdd920a15f6218690630f09f7e48199037b31d96e5c36546cf`,
addresses-section sha256 (compact JSON)
`2b45e56d41364df6262adc321424d71a8a0851f6873ff17a55e65ed82665c657`.
These values have not been re-run with the current query; the owner
needs to re-run the builder once to confirm them (or replace them).

`validate_lookup.py` checks schema, ordering, duplicates and (optionally)
the exact whole-file sha256 (`--sha256`) and the addresses-section
sha256 (`--addresses-sha256`) without needing any private file. With `--reference` and
`--helper` it also resolves a golden set of known Jerusalem addresses
with both an old and the regenerated file through
`parking-report-helper`'s lookup path and compares street codes, house
numbers and ITM coordinates (rows where both files refuse are reported
as DIFF so the refusal reasons stay visible; an identical refusal on
both sides is expected for addresses outside OSM/registry coverage).

## Notes

- OSM has no Jerusalem municipal street codes, so the code list comes
  from the national street registry on data.gov.il (under the site's
  default licence, source cited - section 1 above); address points come
  from OSM. The two are joined
  inside the app by normalized street name, exactly like the pipeline's
  version-1 file behaves.
- Street names mapping to more than one municipal code are dropped from
  the streets section (the resolver refuses ambiguous names anyway).
- The in-app attribution lives in
  `app/src/main/assets/i18n/strings.json` (`licenses.*` keys).

## On-device lookup precedence and updates

The first installed candidate wins: app-specific external files directory,
then noBackupFilesDir, then the bundled development asset. A present but stale
external copy blocks submission even when a matching copy exists later in the
list. This is deliberate fail-closed behavior; replace or remove the stale
first copy rather than bypassing the pin. Missing and mismatched files have
different UI messages.

The pin covers the whole file byte-for-byte. Any regeneration or reformatting
requires an app release carrying the new pin and coordinated installation of
the matching private file. The file itself must not enter this public repo.
Synthetic E2E uses the test-only in-memory directory seam from #185, not an
override of the production pin or an installed-file mutation.
