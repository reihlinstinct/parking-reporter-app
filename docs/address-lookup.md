# Address lookup builder (open data, attributed)

`tools/address-lookup/build_address_lookup.py` regenerates the app's
address lookup (`{"version": 1, "streets": [...], "addresses": [...]}`)
from open, attributed sources. It replaces the municipality-supplied
`addresses.json`, whose licence for publication was never established
and which is therefore kept out of this repository.

## Sources and licences

1. **Street codes and names** - the national street registry "רשימת
   רחובות ישראל" (רשות האוכלוסין וההגירה) on **data.gov.il**
   (resource `9ad3862c-8391-4b2f-84a4-2d4c68625f4b`, locality 3000 =
   Jerusalem). Its סמל_רחוב is the municipal street code the 106 API
   uses (spot-checked: אגריפס -> 613). The dataset page carries **no
   dataset-specific licence**, so the site's default licence applies by
   its own terms: "תנאי השימוש באתר מאגרי המידע הממשלתיים"
   (<https://data.gov.il/terms-of-use>, updated 2025-08-30) - a
   worldwide, royalty-free, non-exclusive licence to use, copy,
   distribute and create derivative works, subject to **citing the
   source**, no misleading presentation or distortion, and no unlawful
   or privacy-violating use. Per those terms, the licence in force at
   retrieval time governs; this build was retrieved 2026-11-08. The app
   cites the source on the Settings -> Licenses screen.
2. **Address points (house numbers)** - **© OpenStreetMap contributors**,
   <https://www.openstreetmap.org/copyright>, licensed **ODbL 1.0**
   (<https://opendatacommons.org/licenses/odbl/1-0/>), fetched from the
   Overpass API inside the Jerusalem municipality boundary (OSM relation
   1381350, mapped to an Overpass area with `map_to_area`).

## Licence status of the output

Under ODbL 1.0 section 1 ("Derivative Database": a database based on the
ODbL-licensed database) and section 4.4(b):

- The **addresses section** of the generated file is a **Derivative
  Database** of OpenStreetMap. It is itself available under ODbL 1.0,
  and the generated file carries top-level `"attribution"`
  ("© OpenStreetMap contributors") and `"license"` (ODbL-1.0 URL)
  keys so the notice travels with the data. Both loaders (the helper
  pipeline's `Addresses` and the app's `StreetDirectory`) read only the
  `version`/`streets`/`addresses` keys and ignore the notices.
- The **combined file** (streets section beside the addresses section)
  is a **Collective Database** under section 4.5(a): the streets section
  keeps its own status (section 1 above) and is not re-licensed.
- The **individual address lookups** the app produces at runtime are
  **Produced Works**; the attribution shown on the Settings -> Licenses
  screen covers section 4.3's notice requirement for them.

Section 4.6 (making the Derivative Database available): recipients can
reproduce the addresses section byte-identically by running the
generator in this repository with the pinned inputs recorded below,
under the boundary condition stated there; it is distributed under
ODbL 1.0. (Owner decision 2026-11-09: the generator route, no release
asset.) Its sha256 is taken over canonical compact JSON
(`json.dumps(addresses, ensure_ascii=False, separators=(",", ":"))`);
the builder prints it on every run, and
`validate_lookup.py --addresses-sha256` checks it with the same
expression. The value from the 2026-11-08 reference build is
`2b45e56d41364df6262adc321424d71a8a0851f6873ff17a55e65ed82665c657`
(see "Reference build" below for how current it is).

The same notice appears on the app's Settings -> Licenses screen.

## Reproduce

```bash
python3 tools/address-lookup/build_address_lookup.py --out addresses.json
python3 tools/address-lookup/validate_lookup.py --candidate addresses.json \
    --addresses-sha256 <printed addresses-section sha> [--sha256 <printed whole-file sha>]
```

The run prints row counts, the pinned inputs, the Overpass database
timestamps (`osm3s.timestamp_osm_base` and `timestamp_areas_base`, when
the server reports them) and both sha256 values to stderr.
`--addresses-sha256` is the check for the ODbL part; the whole-file
`--sha256` also covers the streets section, which drifts with the live
registry (below). Inputs are pinned as follows:

- Overpass query: `[date:"2026-11-08T00:00:00Z"]` as the global setting,
  then `rel(1381350); map_to_area->.jerusalem;` in the same query, then
  `addr:housenumber` + `addr:street` nodes and ways in that area
  (`out center tags`). The date pin covers the address nodes and ways
  and the relation lookup. It does **not** cover the boundary geometry:
  the Overpass documentation states that areas derived from relations
  always represent current data, and that `map_to_area` returns the
  area as last generated by the server's background process
  (<https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL>,
  "By area" and "map_to_area"). So the addresses section is
  byte-identically reproducible **while the boundary relation 1381350
  (and the server's area generated from it) is unchanged**; a later edit
  to the boundary can add or drop points near its edge. The printed
  `timestamp_areas_base` shows which area state a run used.
- National registry resource `9ad3862c-8391-4b2f-84a4-2d4c68625f4b`,
  filter סמל_ישוב=3000, retrieved 2026-11-08, 4,383 records at
  retrieval (4,371 kept, 6 ambiguous name pairs dropped). The registry
  is a live dataset (updated about weekly) and its API has no date pin,
  so a later re-run may pick up registry changes in the streets section;
  the addresses section above is the pinned part (with the boundary
  condition above).

Reference build of 2026-11-08, made with the earlier query form
(`area(3601381350)->.jerusalem;`, the same Overpass area that
`rel(1381350); map_to_area` selects) before the change to
`map_to_area`: 4,371 streets, 22,524 address points, whole-file sha256
`bd1d8f5d49549cfdd920a15f6218690630f09f7e48199037b31d96e5c36546cf`,
addresses-section sha256 (compact JSON)
`2b45e56d41364df6262adc321424d71a8a0851f6873ff17a55e65ed82665c657`.
These values have not been re-run with the current query; the owner
needs to re-run the builder once to confirm them (or replace them).

`validate_lookup.py` checks schema, ordering, duplicates and (optionally)
the exact whole-file sha256 (`--sha256`) and the addresses-section
sha256 (`--addresses-sha256`) without needing any private file. With `--reference` and
`--helper` it also resolves a golden set of known Jerusalem addresses
with both an old and the regenerated file through
`parking-report-helper`'s lookup path and compares street codes, house
numbers and ITM coordinates (rows where both files refuse are reported
as DIFF so the refusal reasons stay visible; an identical refusal on
both sides is expected for addresses outside OSM/registry coverage).

## Notes

- OSM has no Jerusalem municipal street codes, so the code list comes
  from the national street registry on data.gov.il (under the site's
  default licence, source cited - section 1 above); address points come
  from OSM. The two are joined
  inside the app by normalized street name, exactly like the pipeline's
  version-1 file behaves.
- Street names mapping to more than one municipal code are dropped from
  the streets section (the resolver refuses ambiguous names anyway).
- The in-app attribution lives in
  `app/src/main/assets/i18n/strings.json` (`licenses.*` keys).

different schema-valid file need their own override policy and are follow-up,
not a prerequisite to normal lookup.

## Bounded-memory APK loading

The Android bundled loader verifies the unchanged asset SHA-256 in an 8 KiB buffer,
then reopens the immutable APK asset and streams address rows into the directory.
It never holds the whole JSON source string and address-row tree together.
Both the app and fresh-install instrumentation use this same loader.
This fixes the API29 16 MiB heap exhaustion observed while duplicating the source
text in integrated PR669. No larger heap, removed assertion, changed asset or pin
is needed. The generic JVM string loader remains for contract tests.

## Regional online lookup (batch 2, refs #700)

The default no longer packages or loads the 2.3 MB address-point file on first install. A 419,211-byte pinned street/region dependency index is bundled. It contains names, codes, aliases, region bounding boxes and SHA-256 values, not point coordinates or polygon vertices. The verified full-file loader remains available only for optional same-pin local import under advanced settings.

The repository hosts 243 CBS 2022 statistical-area files and one outside-coverage file. Each geographic file contains full WGS84 polygon geometry and its address points; median size is 11,359 bytes, maximum 54,391 bytes. Total geographic files are 2,994,088 bytes, plus 16,712 bytes outside coverage. Geometry is not simplified. These are statistical areas, not neighborhood names. Source/license attribution is in `app/src/main/assets/licenses/CBS.txt`.

For GPS lookup, a local bounding-box index picks candidate region IDs with a conservative halo. Only those static IDs leave the device. In-coverage GPS lookup also loads the pinned 16,712-byte outside-coverage shard as ambiguity evidence: a nearby point across a coverage edge must compete rather than vanish. It never establishes polygon coverage. Downloaded pinned geometry then runs local boundary-inclusive point-in-polygon, preserving holes and multipart regions. Outside CBS coverage never snaps to a nearest region and asks for a manual address. Manual street/crossing lookup loads all regions contributing points to either street, preserving full-city alias ambiguity and unique short-name tail matching. The 383 of 22,627 source points outside coverage remain available in a labeled outside-coverage shard for manual lookup and in-coverage GPS ambiguity checks.

Verified files are cached privately outside Android backup. Wrong hashes, oversize bodies, redirects, network failure or interrupted imports cannot replace a good cache. Offline lookup works for regions already cached, not every unvisited part of the city. An optional full approved local file can supply complete offline coverage. No reporter data, exact address string or exact GPS is sent to the file host. The host sees requested region IDs, including the fixed outside-coverage ambiguity dependency. These IDs reveal the approximate photo area and the host also sees the client IP. Street suggestions come from the local pinned street index without downloading any point file, with the same bounded matching as an imported directory. No paid endpoint, API key or server deployment is needed.

Published version directories are immutable. Do not regenerate, edit, remove or replace anything under `tools/address-lookup/data/v1/` after release. Any changed index, geometry or point data must go to `data/v2/` (or the next unused version), with a matching new bundled index, pin and base URL for new APKs. Retain every old version so existing installations can fetch their original pinned bytes. CI fixes the v1 index hash and verifies every referenced shard hash; updating those pins in place is not a data update procedure.

Confirming a GPS-derived address does not guarantee offline submission. Submission intentionally reloads all shards contributing to the confirmed street, which may include regions not downloaded for the GPS lookup. If one is uncached and offline, submission refuses before creating the municipal client or sending any case. It never reuses a partial GPS directory as complete street data. `RegionalAddressProductionTest` covers a successful GPS address followed by an uncached same-street region that refuses the street reload. Full optional import or previously cached street shards avoid that extra fetch.

The refresh action removes cached files and any optional import, returning to online regional lookup on the next address request. It does not prefetch every region. The clear action removes both kinds of saved data without a network request. UI copy and the precise refresh semantics remain subject to review.

Limitations: the 2022 geography does not prove current municipal boundaries. The current report model does not carry GPS accuracy into lookup, so the conservative halo is not uncertainty-aware polygon selection. Android compilation, actual UI screenshots, APK asset inspection and exact-head CI remain required before this batch is ready. Raw GitHub serving may be unavailable; refusal is visible and last-good cache is retained. The fixed main URL must expose the pinned files after merge; no unmerged-feature activation is claimed.

### Reproducing the regional files

`tools/address-lookup/sources/cbs-jerusalem-2022.geojson.gz` is a lossless compressed copy of the reviewed Jerusalem subset. After decompression, its SHA-256 must be `ad780e9e8a977ad7f55618a4a032af35053b8f3e013de9be7e7b9c7332e02310`. The generator checks this pin and the existing address-data pin before writing anything. Stable IDs are `cbs-` plus the source `YISHUV_STAT_2022` value. Geometry coordinates are carried through without simplification or rounding.

```sh
python tools/address-lookup/build_address_shards.py \
  --dataset app/src/main/assets/addresses.json \
  --polygons tools/address-lookup/sources/cbs-jerusalem-2022.geojson.gz \
  --output /tmp/regional-addresses \
  --allow-outside-cbs-coverage
```

The output index must match `app/src/main/assets/address-index.json`, SHA-256 `3d56c9386db6d48d655ce72141bc224da1233f6ba90374ba7f2471f084ef5dd8`. Every other output must match the corresponding file under `tools/address-lookup/data/v1/`. All 244 shard files and the index were reproduced byte-for-byte from these checked-in inputs.

The compressed source is a disclosed technical derivative of the official CBS source linked in `licenses/CBS.txt`: select locality code 3000 from the 2022 geodatabase, convert EPSG:2039 to WGS84, normalize ring orientation, remove demographic columns, preserve all geometry without repair. The original ZIP hash is recorded with that attribution. Rebuilding this converted snapshot from the original geodatabase requires the same GIS conversion environment and is separate from the deterministic shard build above.
